# Яндекс.Карты: Описание продукта и аудитории

## 1. Тема и целевая аудитория

### 1.1 Тема
**Яндекс.Карты** — это геосервис для построения маршрутов, входящий в экосистему Яндекс.
Сервис позволяет:
- Строить маршруты
- Смотреть расписания всех видов транспорта
- Оценивать загруженность дорог
- И многое другое

**География покрытия:** Россия, страны СНГ и ряд других регионов. [6](https://yandex.ru/support/m-maps/ru/cities-and-countries) [7](https://ppc.world/news/yandeks-karty-obognali-google-karty-po-populyarnosti-v-rossii/)

---

### 1.2 Функционал MVP
Минимально жизнеспособный продукт (MVP) включает в себя следующие ключевые функции:

- **Авторизация пользователя**
- **Построение маршрутов** (на метро и личном транспорте)
- **Оценка загруженности дорог** в режиме реального времени
- **Рекомендация мест** для посещения
- **Поиск локации** по адресу / точке на карте

### 1.4 Ключевые продуктовые решения

В основе продукта лежит ряд технологических и архитектурных решений, направленных на обеспечение бесшовного пользовательского опыта, надежности и скорости работы:

*  **☁️ Оффлайн режим.** 
    При первом просмотре участка карты тайлы кешируются на устройстве. Это обеспечивает мгновенный доступ к карте при повторном использовании (даже при плохой связи) и радикально снижает нагрузку на серверы и затраты на исходящий трафик.

*   **🔄 Единый аккаунт на всех устройствах**
    Хранить всю историю построения маршрутов / поиска локаций в аккаунте юзера, чтобы иметь к ней доступ с разных устройств

*   **⚡️ Динамическая отрисовка карт**
    Разбить карту на тайлы, как это сделано в Яндекс картах, чтобы уменьшить единовременную нагрузку на сеть и ускорить процесс отрисовки маршрута

### 2.2 Технические метрики

#### Расчёт объёма хранения

Расчёт производится для хранения пользовательских данных (история), генерируемых за 1 год использования сервиса. Уникальные данные картографической подложки не учитываются, так как они общие для всех.

| Тип файлов | Расчёт на пользователя | Общий объем |
| :--- | :--- | :--- |
| **История маршрутов** | 0,89 маршрута/день * 365 дней * 2кб  ≈ 0,65 МБ | **~12,4 ТБ** |
| **История поиска (текст)** | 3 запроса/день * 365 дней * 200 байт ≈ 0,22 МБ | **~4,2 ТБ** |
| **Избранное / Метки** | 50 мест * 200 байт (координаты + метаданные) = 0,01 МБ | **~0,2 ТБ** |
| **Кеш карт (временные файлы на CDN)** | Условно храним последние 30 дней активности ~10 МБ [[5](https://istore-d.ru/blog/umnye-tekhnologii/kak-polzovatsya-kartami-na-iphone-bez-podklyucheniya-k-internetu/)] | **~244 ГБ** |
| **Итого (без учета кеша)** | ~0,88 МБ | **~17 ТБ** |

Обоснование значений:
 - 200 байт на одну историю поиска - один текстовый запрос занимает около 20-25 символов, по 2 байта (в utf-8) на каждый + нам нужны метаданные, что еще займет около 100-150 байт, поэтому было взято значение с запасом
 - 2кб на один маршрут - каждая точка в формате geoJSON весит около 40 байт, пусть простой маршрут в городской местности со множеством изгибов имеет 50 точек на маршрут, таким образом получаем около 2кб на маршрут
 - Весь Новосибирск весит 100мб, Москва в 4 раза больше по площади, возьмем ее вес за 500мб, за год предположим прогрузят 500 площадей Москвы, что выйдет в 244 гб на CDN
> **Пояснение:** Расчеты для текстовых данных (история) приблизительны, так как точный объем метаданных, сохраняемых для каждого события, неизвестен. Кеш карт занимает основной объем, но эти данные временные и могут не храниться на серверах в привязке к пользователю вечно.

---

#### Сетевой трафик

При расчёте используется коэффициент суточной неравномерности **k = 2** для определения пиковой нагрузки.

| Тип трафика | Суточный объём (Тбайт/сут) | Средний трафик (Гбит/с) | Пиковый трафик (k=2) (Гбит/с) |
| :--- | :--- | :--- | :--- |
| **Загрузка карт (тайлы)** | 20 млн * 50 тайлов * 20 КБ = **18,62** | **~1 724** | **~3 448** |
| **Построение маршрута (API)** | 6,5 млрд / 365 = 17,8 млн запросов * 2 КБ = **0,03** | **~3,33** | **~6,66** |
| **Поисковые запросы** | 20 млн * 3 запросов * 200 байт = **0,01** | **~1,11** | **~2,22** |
| **Обновление пробок / Данные о местоположении** | 20 млн * 48 мин * 2 обновления в минуту* 0,89 * 50 байт ≈ **0,07** (исходящий) | **~6,48** | **~12,96** |
| **Итого (оценка)** | **~18,73** | **~1 735** | **~3 470** |

Пояснения:
- 50 байт - средний преполагаемый вес пакета типа geoJSON с информацией о точке
- 48 мин - средняя длина пути на автомобиле в Яндекс Картах - 32 км, в среднем автомобиль едет 40 км/ч по городу(примерно), вызодит его путь занимает 48 минут, частоту оттправки возьмем раз в 30 сек
---

#### Расчёт RPS (Requests Per Second)

RPS рассчитывается по формуле:  
**RPS = (DAU × Действия в сутки) / 86 400**

| Тип запроса | Общее кол-во запросов в сутки | Средний RPS | Пиковый RPS (k=2) |
| :--- | :--- | :--- | :--- |
| **Загрузка тайлов карты** | 20 млн * 50 тайлов = 1 млрд | **~11 574** | **~23 148** |
| **Построение маршрута** | 17,8 млн | **~206** | **~412** |
| **Поиск (геокодирование)** | 20 млн * 3 = 60 млн | **~695** | **~1 390** |
| **Получение данных о пробках / ETA** | 20 млн * 48мин * 2 (раз в 30 сек) = 1,92 млрд | **~22 222** | **~44 444** |
| **Итого (оценка)** | **~3 млрд** | **~34700** | **~70000** |

# 3. Глобальная балансировка нагрузки

## 3.1 Функциональное разбиение по доменам

Для оптимизации обработки разнородных запросов и независимого масштабирования сервисов используются следующие домены:

| Доменное имя | Назначение |
|--------------|------------|
| api.yandex.ru/maps | Основное API (синхронизация, поиск, пробки) |
| media.yandex.ru/maps| Передача "тяжёлого" контента (фото, видео, тайлы карты) |
| static.yandex.ru/maps | Раздача статических ресурсов (JS/CSS) |
| yandex.ru/maps | Основной сайт (FAQ, документация, дистрибутивы) |

## 3.2 Расположение дата-центров

Для обеспечения RTT в пределах 50 мс в ключевых регионах присутствия [6](https://yandex.ru/support/m-maps/ru/cities-and-countries) [7](https://ppc.world/news/yandeks-karty-obognali-google-karty-po-populyarnosti-v-rossii/) используется система из 5 основных ДЦ:

| ID | Локация (город, страна) | Обслуживаемый регион |
|----|-------------------------|----------------------|
| DC-MSK| Москва | Центральный федеральный округ, Северо-Запад (частично), Поволжье |
| DC-SPB | Санкт-Петербург | Северо-Западный округ, Ленинградская область, балтийские маршруты |
| DC-SIB | Новосибирск | Сибирь, Дальний Восток |
| DC-KZ | Алматы / Астана (Казахстан) | Казахстан, Средняя Азия |
| DC-BY | Минск (Беларусь) | Беларусь |

**Обоснование выбора:**
**Москва**: Здесь пересекаются все магистральные каналы связи, идущие в Европу, Азию и на юг. Без ЦОДа в Москве невозможно обеспечить низкую задержку для основной массы пользователей из Центральной России .

**Санкт-Петербург**: Снижает нагрузку с ЦОД Москвы, а также дает выход в Европу.

**Новосибирск**: Это стратегическая точка для масштабирования на восток. Размещение ЦОДа здесь позволяет обслуживать Сибирь и Дальний Восток без экстремальных задержек, которые возникли бы при связи с Москвой.

**Алматы / Астана**: Наличие ЦОД в стране обеспечит скорость и соответствие требованиям регулятора .

**Минск**: Размещение серверов внутри страны (как это делают многие провайдеры) обеспечивает лучшее качество связи, чем работа через Москву, и решает вопросы суверенизации данных .

## 3.3 Распределение запросов по ДЦ

Нагрузка распределяется пропорционально активной аудитории регионов, исходя из рассчитанного пикового RPS **~70 000** (п. 2.2). Учитываются не только количественные показатели, но и интенсивность использования сервиса в каждом регионе (actions per user).

| Регион (ДЦ) | Процент трафика | Пиковый RPS | Обоснование |

## 3.4 Схема балансировки

Учитывая специфику Яндекс.Карт (высоконагруженный геосервис с "тяжелым" медиа-контентом и чувствительными к задержкам API-вызовами), для достижения максимальной производительности и отказоустойчивости используется многоуровневая схема балансировки.

*   **Latency-based DNS (GeoDNS)**:
    На основе базы Geo-IP и данных о текущей загрузке каналов пользователю возвращается IP-адрес ближайшего регионального ДЦ с минимальным RTT (Round-Trip Time).

*   **EDNS Client Subnet (ECS)**:
    Для повышения точности определения местоположения клиента используется расширение EDNS0 Client Subnet. Это позволяет DNS-серверу учитывать подсеть клиента, а не только IP-адрес рекурсивного DNS-резолвера, что критично для пользователей, использующих публичные DNS (Google DNS, Cloudflare DNS).

*   **BGP Anycast для критичных API**:
    Несколько ДЦ анонсируют один и тот же IP-адрес для домена **`api.yandex.ru/maps`**. Сетевые роутеры направляют пакеты по кратчайшему маршруту (наименьшее число хопов / AS Path).

*   **Распределенная система кеширования (CDN) для медиа**:
    Для домена **`media.yandex.ru/maps`** (тайлы карты, фото панорам) использование BGP Anycast нецелесообразно из-за риска разрыва длительных TCP-сессий и потери кеша при изменении BGP-маршрутов. Вместо этого применяется:
    *   **Гео-ориентированная CDN:** Запросы направляются на ближайший периферийный узел (PoP), который отдает контент из кеша или запрашивает его из основного ЦОД (origin pull).
    *   **Anycast для DNS CDN:** Сама система CDN может использовать Anycast на своих периферийных узлах для быстрого определения ближайшей точки входа, но это прозрачно для нашей инфраструктуры.

## 3.5 Механизмы регулировки трафика

- **Weighted Round-Robin:** Для равномерного распределения нагрузки между инстансами бэкенда.
- **Active Health Checks**: Мониторинг состояния ДЦ. При деградации сервиса ДЦ автоматически выводится из DNS-выдачи.
- **Client-side Steering**: Клиентское приложение хранит список IP-адресов всех 5 ДЦ и способно самостоятельно переключиться на альтернативный регион при недоступности текущего.
- **Least-loaded:** Для направления запросов на наименее загруженные серверы.
- **Sticky sessions:** Для привязки пользователя к конкретному серверу на время сессии (если требуется, например, для долгих вычислений маршрута).
